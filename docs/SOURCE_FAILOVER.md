# 多音源自动切换（Source Failover）设计与实现

> 目标：用户配了多个音源时，第一个源放不了就自动换下一个；而且**下一首同平台的歌不再等第一个源超时**。
> 代码：`core/source/SourceRouter.ets`（新增）、`core/source/SourceEngine.ets`、`core/player/PlaySession.ets`、`core/settings/PlaySettings.ets`、`views/SourceSettingsView.ets`

---

## 一、问题现象（用户原话）

1. 「配了许多个音源，第一首音源无法播放时，往往不会自动切换到后面的音源」；
2. 「或者第一个音源无法播放时，自动切换到第二个。但是再播下一个同平台的歌时，又会卡半天，等第一个音源超时，然后再请求第二个」。

## 二、根本原因

| 环节 | 改动前的行为 | 造成的现象 |
|---|---|---|
| 音源加载 | 沙箱（一个 WebView）里**同一时刻只挂载一个**源脚本，`loadedSourceId` 只有一个 | 只有「当前音源」会参与解析，别的源根本不会被试 |
| 解析链路 | 只问当前这一个源，失败后再走「换平台 / 报错」 | 第一个源不行 = 整首失败，或只能靠换平台兜底 |
| 请求超时 | 单次解析上限 **60 秒**（`SourceEngine.REQUEST_TIMEOUT`），HTTP 默认 13 秒 | 源卡住时用户干等，最坏一分钟没声音 |
| 失败记忆 | 只有「平台级」冷却（`PlatformHealth`，键是 `音源id::平台`） | 能跳过坏平台，但跳过之后没别的源可用，也没记住「哪个源好用」 |

一句话：**没有「源」这一维度的调度**——只有「平台」维度，而用户手里多的是源。

## 三、算法

### 3.1 路由表：记住「哪个源在哪个平台靠谱」

`SourceRouter` 维护两张表，落在 `filesDir/lx_sources/source_router.json`：

- `routes[平台] = [{id, lastOkAt, failStreak, lastFailAt, lastError}, ...]`
- `caps[音源id] = [它声明了 musicUrl 的平台]`、`names[音源id] = 名字`

候选顺序（`candidates()`）分五段，越前越先试：

```
1. 可信段：该平台成功过且 failStreak < 2  → 按 (失败次数升序, 最近成功降序)
2. 当前已加载的源（若它确实支持这个平台）     → 省掉一次换源加载
3. 降级段：failStreak ≥ 2                  → 按最近失败时间升序（久没失败的先试）
4. 能力已知（声明支持该平台）但还没有历史结论的源
5. 能力未知（从没加载过）的源                → 排最后，加载后即知道它支不支持
```

已知**不支持**该平台的源直接不列（否则每个都要白加载一次脚本）。

### 3.2 单次解析：短预算 + 按次中止

实现在 `core/source/SourceFailover.ets`（`resolveUrlWithSourceFailover`），**播放与下载共用这一份**——
取流能力同源，能放的源当然也能下，没必要两套逻辑各写一遍（写两遍迟早不一致）。
播放只是额外挂了两个回调：切歌取消（`playToken`）与状态行「正在切换到音源「X」…」。

`PlaySession.resolveWithSourceFailover()` 按候选顺序逐个试：

```
候选数 > 1 ：第一个 7s，之后每个 5s，总计 15s 预算
候选数 = 1 ：单次 25s（没有「换人」余地，不能把慢但能成功的解析判死）
```

- 超时由 `SourceEngine.getMusicUrl(..., timeoutMs)` 承担；到点不仅拒绝等待，还会
  `abortNativesOf(解析key)` —— 把**这次解析名下发起的原生 HTTP 请求**一起 abort
  （靠「原生请求 key → 归属的解析 key」的归属表实现），避免后台还在跑、迟到的回调回灌到新沙箱。
- 每个候选前先看冷却表：`PlatformHealth.isCooling(源, 平台)` 命中就跳过，不发那个必败的请求。
- 成功 → `PlatformHealth.markSuccess` + `SourceRouter.markSuccess`（回到队首，**立刻粘住**）；
  失败 → 两个表都记一笔（冷却时长由失败类型决定，见 `PlatformHealth`），继续下一个。

### 3.3 自愈（用户特别点到的三种异常）

| 异常 | 处理 |
|---|---|
| 用户**删掉了**某个源 | `SourceEngine.removeSource()` 立刻 `router.forget([id])`；启动时 `router.init()` 还会拿当前真实音源列表 `purge()` 一遍，指向已删源的记忆全部丢弃 |
| 用户**重新导入/覆盖**了源脚本 | 内容变了（`isSameScript` 为 false）就 `forget([id])`：脚本换了等于换了一套后端，能力与成功记录都作废 |
| 某个源**今天**打不通这个平台 | 连败 2 次 → 降级到队尾（仍会试，成功后立刻回首位）；失败超过 30 分钟 → 计数衰减归零，重新给一次公平机会。冷却表本身按失败类型给 30 分钟 / 5 分钟 / 2 分钟 |

### 3.4 下载链路

`DownloadManager.resolveUrl()` 走同一个 `resolveUrlWithSourceFailover`：

- 档位协商仍是 `pickQuality`（母带 / Hi-Res 与播放一致），失败再 `fallbackQuality` 降档重试；
- 需要换源时，先问 `SourceEngine.hasPendingResolve()`：**如果有别的解析正在等沙箱回调
  （比如用户刚点播放），这次下载就不换源**——换源会重新注入脚本并中止那次解析，
  宁可让这次下载失败，也不能把正在起播的歌打断。
- 反过来，**播放不受下载影响**：`isPlayback: true` 的那次解析换源时不看这个标志。
  一句话规则：用户正在等的播放优先，后台任务让位。

### 3.5 预取的特殊处理

后台预取**不换源**：

- 若路由表说这个平台首选另一个源（`preferredFor() != 当前源`），预取直接跳过并记日志。
  换源要重新注入脚本，会打断正在播放的这次会话，不值得为「还没轮到的歌」冒险；
  等真切到这首时，播放链路会一次性把源切好，之后预取照常工作。
- 预取自身也给 8 秒预算，避免一个卡住的源长时间占着沙箱。

### 3.6 按音质选源（2026-11-19 补）

真机验证时发现的坑：用户开「拓展音质 = 母带」，但**当前加载的源没声明母带**（比如只声明了 128k/320k/flac），
于是 `pickQuality` 只能退回 flac —— 另一头明明有个声明了母带的源，却永远不会被用到。

所以路由表多记一列「每个源在每个平台声明了哪些音质档」（`RouterFile.quals`），并规定：

1. `PlaySession` 在**查缓存之前**就确定「想要的那一档」：只要还有任意源声明了它，就按它去找缓存/解析
   （否则 flac 的地址缓存会直接命中，解析链路——唯一会换源的地方——根本不会执行）；
2. 候选顺序把「声明了目标档」的源提到前面（组内保持原有「成功过优先」的顺序）；
3. 第一轮只试声明了目标档的源，避免把时间花在明摆着给不了的源上；
4. 换源之后**按新源重新协商**一次档位（同一个 musicInfo 在不同源上能拿到的档不一样），
   并把实际用的档位回写给播放/下载（否则界面显示 320K、缓存键也按 320K 存，和真正在放的母带对不上）。

真机实测（2026-11-19）：念心音源（3 档）加载中 → 播放 QQ《晴天》→ 自动切到 ikun 音源（8 档含 master）→
日志出现 `pick tx -> master` 与 `"quality":"master","url":".../AI00001diEF43yBtZk.flac"`，
`ProResampler inRate:192000`，播放正常出声。

### 3.7 兜底

候选全部失败时：先 `restoreLoadedSource(previousId)` 把原来那个源加载回来
（`loadSource` 中途失败会把引擎停在「未初始化」，不恢复的话用户接下来连别的平台都放不了），
再把最后一个错误抛给上层 —— 上层照旧走「换平台」（`switchSourceAndResolve`）或报错。
所以**关掉开关**（`PlaySettings.isAutoSourceSwitch() == false`）时，行为与改动前完全一致。

### 3.8 解析成功 ≠ 地址能用：播放失败也要换源（2026-11-19 补）

群反馈（「五一」，2026-11-19 20:31）：

```
播放错误：IO Resource Not Found: IO error, IO resource not found,
requestError: true, errorType: server error, errorCode: 404, …
```

这是**音源给的直链已经废了**（服务端 404），不是解析失败：脚本正常返回了 url，播放器一拉就 404。
改动前这种只会原地报错，点重试还是同一条死链 —— 因为地址缓存里存着它。

**判据刻意放宽**（群主原话：「不管什么原因，只要播放失败、最后没有放出来，就说明这个源有问题，
你就应该往下换源」）：不挑错误类型，只看结果。`isDeadUrlError()` 只用来区分日志口径
（`dead url` / `no sound`），不影响是否重试；重试走 `PlaySession.onPlayerState('error')`
→ `retryAfterPlayFailure`：

1. 记一笔到**给这条链的源**头上：`SourceRouter.markFailure(source, platform)` +
   `PlatformHealth.markFailure` —— 路由表是**按平台**存的（`routes: 平台 → SourceRoute[]`），
   所以「同一个源在 A 平台能用、D 平台不能用」是分开记账的，下次同平台会换人；
2. `MediaCache.dropMusicUrl` 丢掉地址缓存 —— 不丢的话重放会再次命中同一条废链；
3. 解析时把它排掉：`FailoverHooks.skipSources` 让候选里去掉这些源（`resolvedSourceId`
   在解析成功时记下，可累计多个），换别的源重新取流；
4. 同一首**最多 3 次**，3 次都拿不到能放的链就认命报错，避免死循环；
5. 最终失败才弹提示，且文案经 `friendlyPlayError()` 翻译（「音频地址已失效（音源返回 404）」等），
   不再把系统原文糊到界面上。

日志关键字：`play failed on %s from %s (%s), retry #%d` / `play failure: no retry left`。

**已知未覆盖**：下载链路拿到 404 时不会自动换源重试（下载失败即失败），见第七节。

### 3.9 歌词的跨平台兜底（2026-11-19 补）

群反馈（「柒の染™」）：周杰伦《发如雪》在酷狗下显示「无歌词，请欣赏」，
但同一首在别的平台有词 —— 「周董的歌有的有歌词有的没有」。

原因在取词匹配方式：酷狗歌词搜索按「歌名 + hash + 时长」找候选（见 `PlatformLyric.kgLyric`），
老歌 / 冷门版本经常一条候选都没有；而**歌词本身是公开资源**，与在哪个平台取流无关。

现在 `PlaySession.fetchLyricRemote` 在本平台取不到带时间轴的词时，会
`lyricFromOtherPlatform()`：按「歌名 + 歌手」在其它平台（tx/wy/kw/kg/mg）搜同一首，
用与换源同一套 `strictlySameSong` 严格匹配（歌名、歌手规范化后必须完全相等），
匹配到就取那个平台的词。任何一步失败都直接放弃，不影响播放。

日志关键字：`lyric borrowed from another platform: %s / %s`、`lyric fallback %s failed`。

### 3.10 显示档位 vs 实际拿到的档位（2026-11-19 记录，未改代码）

真机测试时注意到一个「看起来像 bug」的现象：酷狗某首曲目播放页音质钮显示「母带」，
日志里 `available=[128k,320k,flac,flac24bit]`（曲目自带的 `_types` 没有 master），
实际解析出的链接带 `_quviper_`。

排查结论：**这不是本项目的显示错误，是音源侧的档位口径**。把设备上的音源脚本拉下来看，
ikun v27 的声明是：

```
kg: ["128k","320k","flac","flac24bit","hires","atmos","master"]
```

即它对 kg 平台**声称**支持母带；而播放页/音质面板列的就是「源声明的档位 ∩ 曲目提供的档位」
（拓展档按 `extendedBySourceOnly` 只看源声明，否则 QQ 母带永远列不出来）。
至于请求 master 之后源的后端实际返回哪一档（`viper_clear` 还是真正的母带文件），
由那个源自己决定 —— 洛雪原版同样是「显示设置/声明的档位」，不校验 URL 的真实码率。

所以这里**刻意不做「按 URL 猜码率、把显示改小」**：URL 里的 `_quviper_` 这类标识
各平台含义不一，猜错就会把真母带显示成 flac24bit，反而误导用户。
真要解决，得让源作者把 kg 的 master 映射到真正的母带接口。

### 3.11 「开了自动切换反而放不了」的结构性修复（2026-11-27）

群反馈（2026-11-19 14:06 / 14:10，自取其乐）：点了自动切换反而放不了，好像自动调到别的源
然后播放失败；能用的源也要转一会儿，怀疑被自动切源当成不能播放直接换掉了。关掉开关就能听。

排查结论：**不是单次判据的问题，是候选顺序 + 时间预算的结构性问题**：

1. `SourceRouter.candidates()` 把「历史成功过的源」排在**当前已加载的源前面**。在某平台还没有
   历史记录时（很常见），当前这个本来能用的源被排到后面；
2. 第一个候选只给 7 秒（多源时），而「能用但慢」的代理型音源往往要 10 秒上下 —— 被当成坏源切走；
3. 换源要 `loadSource()` 重新注入脚本（重置引擎、中止在途请求），新源一旦返回一条地址就立刻算成功，
   哪怕这条是死链；播放器一拉 404 又触发「失败换源」，3 次后报错。
4. 关掉开关走的是 `single()`：只用当前源、给 60 秒，所以「关掉就能放」。

修复（原则：**开着自动切换的成功率不得低于关着**）：

- `candidates()` 把**当前已加载且声明支持该平台**的源永远 push 第一位；路由记忆排在它后面。
  一旦真的切到新源并成功，新源就成了「当前源」，下一首自然仍是第一，记忆机制的目标不变；
- `SourceFailover`：第一个候选若是当前源，给 `SINGLE_TIMEOUT_MS`（25 秒）而不是 7 秒；
  只有它在路由表里已连续失败 ≥2 次（确实坏了）时才仍给短预算，避免坏源每首卡 25 秒；
- 总预算相应把这一发让出来（`BUDGET_MS + firstBudget`），且第一发已用长预算试过当前源时
  不再跑 `lastChance`（省掉一次重复的 25 秒）。


## 四、开关与观测

- 设置 → 音源设置 → **多音源 / 自动切换音源**（默认开）。
- 日志关键字（`hilog` tag = `PlaySession` / `SourceEngine` / `SourceRouter`）：

| 关键字 | 含义 |
|---|---|
| `source %s failed on %s` | 某个源在该平台解析失败，已记账 |
| `skip cooling source %s on %s` | 冷却中，直接跳过 |
| `switch source for playback: %s` | 为播放换源（状态行会显示「正在切换到音源「X」…」） |
| `source failover budget exhausted` | 15 秒预算用完，停止换源 |
| `restored previous source after failed failover` | 全失败后已恢复原源 |
| `prefetch skipped: preferred source is %s` | 预取因首选源不同而跳过 |
| `skip switching to %s: another resolve pending` | 有解析在等回调（通常是播放起播），这次不换源 |
| `mark failure: %s/%s streak=%d` | 路由表记一次失败 |

## 五、取舍（为什么不是别的做法）

1. **不为每个源常驻一个沙箱**：一个源脚本几 MB、一个 WebView 沙箱，内存吃不消；改成「按需加载 + 记忆」，稳定期只付一次加载成本。
2. **不做并行竞速（谁先返回用谁）**：沙箱是单线程的，注入两个脚本本身就会互相打断；而且并行请求会让「同一个 key 的回调归属」变得不可判。
3. **单源不放短超时**：慢≠坏。多源时才值得为「换人」牺牲一次可能成功的解析。
4. **预取不主动换源**：宁可慢一首，也不要为了预取打断正在放的这一首。

## 六、验证清单

- [ ] 两个源，A 对 tx 不可用（如回 403）、B 可用：播放 tx 歌 → 自动切到 B 并出声，日志出现 `switch source for playback: B`；
- [ ] 紧接着播第二首 tx：**不再调用 A**（日志无 A 的失败行，`resolve` 明显变短）；
- [ ] 把 B 删掉后播第三首：不出现对 B 的任何请求（启动 `purge` / 删源 `forget`）；
- [ ] 关掉「自动切换音源」：行为与 1.0.8 之前一致（只问当前加载的源）；
- [ ] 单源 + 慢源（解析 10 秒以上）：仍然能成功（25 秒预算）；
- [ ] 源脚本损坏：加载失败后其余平台仍可播放（`restored previous source`）；
- [ ] 下载与播放同源：播放某首歌成功后立刻下载同一平台另一首 → 不再撞坏源、直接成功；
- [ ] 下载母带：开拓展音质选「母带」，下载一首 QQ 歌 → 拿到母带文件；无权限时自动降档而不是失败；
- [ ] 播放正在解析时点下载 → 下载失败/走当前源，**不会**打断那次起播（日志 `skip switching ... another resolve pending`）。
- [ ] 播放失败换源：某源给的链放不出来（404 / 500 / 拉流中断）→ 自动丢掉死链、换源重来并出声
      （日志 `play failed on … retry #1`）；同一首连续 3 次都失败就停止重试并提示
      （日志 `play failure: no retry left`）；
- [ ] 歌词跨平台兜底：播一首酷狗老歌（如周杰伦《发如雪》）→ 有歌词；
      日志 `lyric borrowed from another platform`；
- [ ] 切页签不抢播：冷启动后点「我的」→ 正在播的歌不变；点「探索」且本来没在播 → 心动模式正常起播。

## 七、未做（后续可选）

- **下载链路的 404 重试**：播放已能「失效地址 → 换源重来」，下载拿到 404 时还是一次失败收场，
  可复用 `retryDeadUrl` 的同一条思路（丢弃该 url 缓存 + `skipSources` 重解析 + 重下）；
- 冷启动时**预热**首选源（现在首个 tx 歌仍需一次换源加载，约 1–2 秒）；
