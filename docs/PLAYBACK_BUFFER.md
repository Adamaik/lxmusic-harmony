# 弱网下的播放流畅性

目标：网络时好时坏的时候，听歌尽量不卡顿、不出现「响一下卡一下」。
**不做自动降音质**（用户要听的就是选定的那一档）。

相关代码：

| 位置 | 职责 |
| --- | --- |
| `core/player/LxPlayer.ets` | 播放策略（缓冲区 / 起播水位线）、缓冲水位事件、给缓存让路的判断 |
| `core/music/AudioCache.ets` | 播放缓存：分块下载、可续传、按优先级排队、播放优先、「缓存时自动下载」开关 |
| `core/download/DownloadManager.ets` | 「缓存时自动下载」时接手：整份下载到下载文件夹，播放挨饿时先不开工 |
| `core/player/PlaySession.ets` | 下一首预取（解析地址 + 排缓存任务）、缓冲状态透给界面 |
| `core/player/ShuffleBag.ets` | 随机播放「一轮不重复」的抽签袋（预取抽签不占名额） |
| `views/PlayerView.ets`、`views/MiniBar.ets` | 缓冲时播放钮转圈 |

## 1. 播放器侧：把缓冲区拉满，起播/恢复等够再出声

`LxPlayer.prepareWithStrategy()` 在 AVPlayer 进入 `initialized` 时（`prepare()` 之前，
这是 `setPlaybackStrategy` 唯一可用的状态）设两个值：

| 参数 | 取值 | 作用 |
| --- | --- | --- |
| `preferredBufferDuration` | 20 | 缓冲区**能播多久**，单位是**秒**，官方取值范围 `[1, 20]`，所以 20 秒就是平台硬上限（不是 20MB） |
| `preferredBufferDurationForPlaying` | 8 | 起播 / 卡顿后恢复的水位线（秒，API 18+，范围 `[0, 20]`）。默认那条线在弱网下只有约 1 秒的量，表现为「响一下、卡一下」；攒到 8 秒再恢复，代价是起播多等一会儿，换来连续播下去 |

依据：`preferredBufferDuration` / `preferredBufferDurationForPlaying` 的官方接口说明
（`devecocli docs read "API参考/Media_Kit_媒体服务/ArkTS_API/ohos_multimedia_media_媒体服务_/Interfaces_其他/arkts-apis-media-i"`），
以及官方《在线视频播放卡顿优化》实践。该实践里还有一句「缓冲区大小 = 该值 × 1MB」——
那是**视频**场景按码率把秒数折成字节的启发式换算，对音频不成立，别当成 MB 读。
它的实测结论（缓冲区越大卡顿率越低：5MB 65.79% / 10MB 28.95% / 20MB 5.26%）方向上是通用的。
设策略失败不影响播放（退回系统默认），见该方法里的 try/catch。

设完策略后订阅 `bufferingUpdate`，把三个值记下来：

- `BUFFERING_START` / `BUFFERING_END`：播放器开始/结束等数据（此刻声音是断的）；
- `CACHED_DURATION`：缓冲区里已缓冲的数据还能播多久（`getCachedMs()`）。

`buffering` 与播放状态分开：缓冲时 AVPlayer 的状态仍是 `playing`，所以界面用
`AppStorage` 里的 `ps_buffering`（`K_BUFFERING`）单独显示成转圈（播放页与迷你栏的播放钮），
否则用户看到的是「暂停图标 + 没声音」。

### 进度条上的缓冲段

播放页进度条按惯例画三段（`PlayerView.bufferTrack`）：整条底的浅色轨道、**已缓冲段**（更亮的灰）、
已播段（白）。系统的 Slider 只有一条轨道，所以自绘一条垫在 Slider 底下，把 Slider 的
`trackColor` / `selectedColor` 设成透明 —— 拖动 seek 仍然归 Slider，几何上左右各让出半个滑块
（`TRACK_INSET`）与它的轨道两端对齐。

灰段画的是**播放器本地已加载到哪儿**（`PlaySession.pushBuffered` → `K_BUFFERED_SECONDS`），
口径与业界一致：

| 平台 | 对应的东西 |
| --- | --- |
| HarmonyOS | `AVPlayer.getLoadedTimeRanges()`（API 26，返回 `[min, max]` 毫秒区间列表） |
| iOS / macOS | `AVPlayerItem.loadedTimeRanges` |
| Web（HTML5 / MSE） | `HTMLMediaElement.buffered`（TimeRanges） |
| Android（ExoPlayer/Media3） | `Player.getBufferedPosition()` → `SeekBar.setSecondaryProgress()` |

两家进度条上那条浅色段画的就是它：**播放器自己已经拿到手、不用等网络就能播到的那一段**。
实现：`LxPlayer.probeLoadedRange()` 每秒主动问一次（跟进度同一个节奏），取区间里最远的右端，
只增不减（回退 seek 时已加载的数据还在本地）；本地播放整首都在本地，直接整条画满。

两条底线：不超过整首时长；不短于当前播放进度（灰段短于白段没法看）。

设备不支持 `getLoadedTimeRanges`（低于 API 26）时自动退回事件那套
（`AVPlayer` 的 `CACHED_DURATION`，算法见下），一次失败就不再问。

#### 别拿"我们自己的整首缓存"画灰段（走过的弯路）

中途有一版灰段是拿 `AudioCache` 的整首下载进度画的（"已下字节数 / 文件总大小"）。它看起来能
一路涨到结尾，但**是假的**：那是同一首歌**另一条连接**下的副本，正在播的这一轮播放器看不到它，
拿它画等于告诉用户"能播到这儿"，而实际上断网就断在那儿。现在灰段只用播放器自己的加载区间，
我们那份缓存进度只在「我的 → 缓存」里看占用。

#### 为什么不能只信播放器的 bufferingUpdate（真机实测）

AVPlayer 的 `CACHED_DURATION` 是「已缓冲数据还能播多久」（前量），官方实践样例的算法是
`bufferedEnd = max(bufferedEnd, 当前进度 + CACHED_DURATION)`，必须取 max：这个值会来回波动，
而缓冲终点只增不减；少了 max 就会出现「灰段永远比已播长固定一截」的假象（拿旧前量跟着
播放头一路加）。`LxPlayer.getBufferedEndMs()` 就是照这个算法实现的，并且不会短于当前进度。

但**它不足以让灰段涨到结尾**。真机实测（`hdc shell hilog | grep LxPlayer`）：

```
bufferingUpdate: cached 522ms,  at 0ms -> end 522ms      ← 25 条全挤在 120ms 内
...（每次 +522ms，at 一直是 0ms）
bufferingUpdate: cached 13061ms, at 0ms -> end 13061ms
（之后整场 ~2 分钟、跨两首歌，再无一条）
```

也就是上手阶段报一批水位、之后就不再报：只靠它，灰段最多画到十几秒就定住，
再被「不短于播放进度」这条底线一压，看起来就是**灰段贴着白段、完全没有提前量**。

#### 缓存下载的让路门槛也改过（同一个坑）

`AudioCache` 是否开工由 `LxPlayer.canUseBandwidthForCache()` 决定。最初写的是
「正在播时，缓冲区余量 ≥ 30 秒才让下」—— 而上面那批水位只报到 13 秒，于是**播放期间
这条线永远不成立**：整首歌都不下缓存，灰段自然没有东西可长。真机上表现为
「一直贴在播放进度上，一息屏（播放状态不再是 playing）就一下子跳到满」。

现在只看**真能测到**的三件事：播放器**正在等数据**（`buffering`）、**正在起播**（`loading`）、
或者**进度已经 3 秒没动**（`STALL_MS`，自己数出来的卡顿）→ 不让；其余时间都让，
缓存**按网络能给的速度下**（不设人为限速：加了限速只会让灰段"匀速直线"地爬，是假的节奏）。

诊断：`hdc shell hilog | grep "buffer bar"`，每 5 秒一条，把灰段的全部输入打出来：

```
buffer bar: buffered 42s / total 158s (progress 38s, player end 13s, cache 27%, local no)
```

哪一路没动，一眼就能看出来（cache 一直是 0% → 缓存在让路 / 没开工）。

#### 第一块不带 Range 的坑（真机日志）

分块下载最初写成「第一块不带 `Range`（怕服务器不认 `bytes=0-`），后续块才带」。结果服务器对
不带 Range 的请求**整份返回**，于是「下载进度」只有 0% 和 100% 两个状态 —— 进度条上是
「先停在最短的位置，然后突然跳满」：

```
00:20:24.609  buffer bar: buffered 13s / total 211s (progress 4s, player end 13s, cache 0%)
00:20:27.913  cache file total: 3381089 bytes (kw_628909_128k.mp3)
00:20:27.921  cached kw_628909_128k.mp3, 3381089 bytes      ← 总大小和「下完」在同 1 毫秒
00:20:29.633  buffer bar: buffered 211s / total 211s (cache 100%)
```

现在**每块都带闭区间 `Range: bytes=a-b`**（开区间那种写法才是不稳妥的那个）。另外进度条的
两段都加了 260ms 的宽度过渡（`TRACK_ANIM_MS`），分块长出来时看着是连续走而不是一格一格跳。

## 2. 播放缓存给播放让路

缓存和播放走同一段网络，两边一起抢的结果就是正在听的这首卡顿。规则集中在
`LxPlayer.canUseBandwidthForCache()`：

| 播放器状态 | 让不让下缓存 |
| --- | --- |
| 正在等数据（`buffering`） | 不让：网络全给它，先补上缓冲 |
| 起播 / 切歌中（`loading`） | 不让：它要抢首屏缓冲 |
| 正在播、但进度已经 3 秒没动（`STALL_MS`） | 不让：自己测出来的卡顿 |
| 正常播放 / 暂停 / 停止 / 空闲 / 出错 | 让：缓存按网络能给的速度下 |

（这里前后删过两版"人工节奏"：一是「缓冲区余量 ≥ 30 秒才让」，二是「起播后先让 4 秒」。
两版都有同一个毛病 —— 拿不靠谱的信号去卡缓存，结果要么整首不下、要么灰段开头干等几秒。
现在只用**真能测到**的信号：播放器在等数据、在起播，或者进度停住。）

缓存侧（`AudioCache`）据此调度：

- **一次只下一个任务**，按优先级排队：正在播的那首 > 预取的下一首；
- **分块下载**（`CHUNK_BYTES` = 64KB，**每块都带 `Range`**）：每块之间检查一次能不能用带宽，
  轮到让路就停下不发下一块 —— 流式 `requestInStream` 一旦开闸只能整个掐断，掐断就白下，
  所以改成块状；
- **可续传**：没下完的留在同名 `.part`，下次从已下字节数接着下（`bytes=N-`）；
  服务器不认 `Range`（回 200 整份）时也能收尾，只是失去暂停能力；
  同名文件换了地址（音源刷新）则从头下，避免两段拼成坏文件；
- **失败退避**：一块没下成隔 `RETRY_DELAY_MS` 再试，不空转；`416` / 不足一块都按「下到头」处理；
- **等带宽的时间不占资源**：只挂一个单次定时器隔几秒回来看一眼，缓冲一结束由
  `PlaySession.onPlayerBuffer` 叫一声 `resumeWaiting()` 立刻接着下，不靠轮询。

淘汰策略不变：整首下完才改名进索引（`.part` 永远不算可播放缓存），上限默认 512MB、
LRU 淘汰，上限设 0 即关闭；进程重启时残留的 `.part` 当废料清掉（`reconcile`）。

## 3. 预取下一首

`PlaySession.prefetchNext()` 在当前这首开始播之后运行，把「切歌那一刻的活」提前干掉：

1. 解析下一首的播放地址存进地址缓存（`MediaCache`），切歌时命中缓存、不必现场解析；
2. 把音频交给 `AudioCache.prefetchSong()` 慢慢下（优先级低于当前这首），下完切过去
   就是读本地文件 —— 不联网、不缓冲。

下一首是谁按播放模式算（`prefetchIndex`）：

| 播放模式 | 预取的下一首 |
| --- | --- |
| 单曲循环 | 不预取（下一首就是它自己） |
| 列表循环 | 下一首；最后一首回到第一首 |
| 顺序播放 | 下一首；最后一首到头则不预取 |
| 随机播放 | 抽一签并**预订**下来，切歌时用这一签 |

随机播放这一签的关键是「抽而不占名额」：`ShuffleBag.pick(..., mark)` 的 `mark=false`
只看看是谁、不记进本轮已放 —— 预取的那一签随时会因用户手动切歌而作废，不能因此
把一首歌从本轮里划掉。真正切到它时才 `markPlayed`。这条规则有单测（`ShuffleBag.test.ets`：
一轮内不重不漏、预取抽签不占名额、换队列重开一轮、上一首回退的记账）。

拿不到 `musicInfo` 的条目跳过预取：那要先按歌名搜一次，代价比预取本身还大，
留到真正切过去时走 `ensurePlayable()`。

## 与「下载」的区别

| | 播放缓存 | 下载（我的 → 下载管理） |
| --- | --- | --- |
| 触发 | 播放时自动，可关（上限设 0） | 用户点下载，或开了「缓存时自动下载」后播放时自动 |
| 落盘 | 沙箱 `files/lx_media_audio/` | 系统 `Download/<应用名>/` |
| 淘汰 | LRU，受上限约束 | 长期保留 |
| 优先级 | 给播放让路，可被中断续传 | 2 并发队列，独立于播放（自动排进来的也给播放让路，见下） |

播放时优先用「下载好的文件」→ 再「播放缓存」→ 最后联网（`PlaySession.playAt` 里的顺序），
所以下载过的歌离线也能放。

### 「缓存时自动下载」（缓存设置里的开关）

打开后边听边存不再由 `AudioCache` 做：播放 / 预取时把这首歌排给 `DownloadManager`，
文件落到 `Download/<应用名>/`，在「我的 - 下载管理」里能看见、能单独删
（封面与歌词一起嵌进去，走的是同一套下载链路）。开的时候会弹一次确认 ——
下面这几条与「缓存」的直觉不一样，先讲清楚再开。

| | 关（默认） | 开 |
| --- | --- | --- |
| 落盘位置 | 沙箱 `files/lx_media_audio/` | 系统 `Download/<应用名>/` |
| 上限 | LRU，受「缓存上限」约束 | 不生效：文件一直留着，由用户在下载管理里删 |
| 删除 | 只能在缓存设置里「清空」 | 删掉那条下载：本地这份就没了，下次播放重新下 |
| 给播放让路 | 分块下载，播放挨饿时停下（可续传） | 整份下载；播放挨饿时**先不开工**（等下次调度），开工后不再中断 |

实现上的几个取舍：

- **播放层不 import 下载器**：下载层要用到播放层的 `SongItem`，两边互相 import 就成环了。
  所以入口注册在叶子模块 `core/download/DownloadIndex.ets`：下载器 init 时
  `setAutoDownloadHandler()` 注册，播放层只按 `AutoDownloadSong` 这个窄接口说话 ——
  与「已下载文件索引」是同一个理由。
- **交给下载器时把沙箱里那份缓存删掉**（`AudioCache.dropKey`）：同一首歌不必占两处地方；
  更要紧的是用户删掉下载之后「本地这份就没了」得成立 —— 缓存里留一份的话照样能离线放。
  正在播的那份不删（删了播放会断），等切歌后再收。
- **下载器不收的照旧走缓存**：WebDAV 云端歌、没有 `musicInfo` 的条目（`enqueue` 返回 null）
  以及下载器还没 init 的时候。不能让一首歌既下不了又缓不上。
- **上限设成 0 也不清空缓存**：开着这个模式时上限本来就不生效，否则「上限 0 + 自动下载」
  的组合会顺手把沙箱里的文件全删掉。关掉开关时才按现有上限淘汰一轮。
- **自动下载排在手动下载后面**（`DownloadManager.nextWaiting`）：用户正在等的那一下
  不该被「边听边下」那批堵住。
- **开启前已经在沙箱里的缓存不会自动搬走**：那些歌照旧从缓存播（本地命中就不会排下载），
  沙箱里那几首也照旧留着。想清掉就在缓存设置里「清空」一次，之后播到的歌都进下载文件夹。


## 领先量为什么停在 20 秒左右（以及怎么才能变成「半首歌」）

真机实测（API 26）：灰段（播放器已加载区间）的领先量稳定在 **13~18 秒**，即使我们自己的整首缓存
已经 100% 下完（3.2MB 约 2 秒下完）也是这个数。这不是 bug，是两道硬约束叠出来的：

1. `preferredBufferDuration` 的取值范围就是 `[1, 20]` **秒** —— 20 秒是平台给的硬上限；
2. 播放器的流缓冲和 `AudioCache` 是**两条独立连接**：我们那份缓存下到哪儿，播放器看不到
   （所以按上面的结论，也不能拿它画灰段）。播放器的领先量只由它自己那条连接决定。

顺带说明为什么不能「拿我们的缓存喂给播放器」：AVPlayer 正在播的这条流已经在推进，
它的加载区间不会因为我们另存了一份副本而前移。想真正把领先量做到整首，只有两条路：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A. 缓存下完后切到本地文件** | 整首在沙箱落盘后重新起播同一个文件（`playLocal`） | 重建 AVPlayer 时有约 0.2~0.5 秒的音频空档；要加三道保护（剩余时长还够 / 文件完整可读 / 失败就静默回退到流） |
| **B. 提前预缓存（推荐先做）** | 不碰播放链路、零静音风险：打开列表 / 歌单时把前 N 首排队预缓存（WiFi 门控），靠已有预取机制把「领先=整首」变成常态 | 要占带宽与存储，得配合上限与「仅在 Wi‑Fi」开关 |

B 是当前更划算的那个：它复用已经写好的 `AudioCache` 优先级队列与下一首预取，
不改播放链路，也就没有静音风险。A 更适合当成兜底（弱网、且这首歌已经落到本地时）。

| 缓存让路与续传 | `hdc shell hilog \| grep AudioCache`：应能看到 `cache yields to playback at N bytes`（让路）、`cache chunk failed at N bytes`（失败退出）、`cached <name>, N bytes`（下完落盘，字节数应大于续传点） |
| 预取下一首 | 列表循环下放过第一首后切第二首，`MediaCache` 命中 + 播放缓存命中，切歌应瞬时出声 |
| 随机播放不重不漏 | 随机模式下连放一整轮，队列里每首歌恰好出现一次（预取不得把歌从本轮划掉） |
