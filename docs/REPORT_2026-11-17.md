## 三、探索推荐「全是老歌」的根因（代码级确凿）

不是「音乐池来源旧」这么简单，是**打分里的新歌信号被废掉了**：

1. `HeartRadio.docOfItem()` 把所有全网候选的 `doc.addedAt` 一律写成 **0**；
2. `HeartEngine.isFresh(doc)` 在 `addedAt <= 0` 时直接返回 false ⇒ **权重 0.3 的「新歌曝光」对所有候选恒为 0，等于这条特征不存在**；
3. 于是排序只剩 `dot`(1.0) / `taste`(0.6) / `affinity`(0.3)，其中 `affinity` 就是「熟悉艺人/专辑」加成，而画像来自**你自己的播放历史 + 收藏 + 本地曲库**（老歌居多）⇒ 越像历史越靠前，越推越老；
4. 候选池结构也偏老：榜单取的是洛雪写死顺序的**前 3 张**（不保证是新歌榜）、歌单取 `sortListOf[0]`（第一个分类，含义不明）、艺人作品取常听艺人 3 人 × 30 首（天然老歌），且三条入口的失败全被静默吞掉，真机上根本看不出哪条挂了。

### 修法（4 个文件）

| 改动 | 位置 | 说明 |
|---|---|---|
| 新增候选新鲜度字段 | `core/heart/HeartTypes.ets` | `HeartDoc.freshBoost: number`（0~1），注释写明「不是真实发行时间，平台歌拿不到，只能由来源+榜内位置推断」 |
| 让新歌权重生效 | `core/heart/HeartEngine.ets` | `pick.fresh = max(isFresh ? 1 : 0, doc.freshBoost)`；权重 0.3 → **0.45** |
| 按榜单名挑榜 | `core/heart/HeartPool.ets` | `boardFreshness()`：新歌/飙升/抖音热歌/网络歌曲/抖快/流行指数 = 0.9，热歌/TOP500/音乐风向 = 0.65，经典/怀旧/金曲/老歌 = 0.1，其余 0.3；`pickBoards()` 按权重稳定排序挑 3 张 |
| 榜内名次衰减 | 同上 | `freshBoost = 榜名权重 × (1 − rank/total)` |
| 歌单入口改造 | 同上 | 分类优先「最新→新歌→热歌」；**`playlistLooksOld()` 过滤「新歌单装老歌」的专辑盘**（名字含经典/怀旧/老歌/金曲/珍藏/回忆/年代，或含早于「今年-2」的年份） |
| 艺人入口收紧 | 同上 | 3 人 × 30 首 → **2 人 × 20 首**，只给低新鲜度 0.15 |
| 池子排序 | 同上 | 返回前按新鲜度稳定排序，重复歌曲取各入口最大值 |
| 可观测性 | 同上 | 每个入口一条 hilog（取到/新增/失败原因）+ 一条汇总：`池子 N 首｜榜单…｜歌单…｜艺人…｜平均新鲜度…` |

## 四、顺手修掉的 5 个既有问题

### 4.1 离线自检污染音源与播放缓存（高）

**真机现象**：点「一键离线自检」后，当前音源被换成内置示例源（`musicUrl` 固定 `https://example.com/test-audio.mp3`），之后所有播放 404；坏地址还被写进播放缓存，重启自动恢复播放也弹 404。

**根因**：`runOfflineSelfTest` 直接操作**全局单例** `SourceEngine`（导入 → `loadSource`），而 `loadSource` 成功会 `saveActive(id)` 把示例源写成当前/上次使用音源；坏缓存是自检后用户点播放时 `PlaySession` 把 404 地址 `saveMusicUrl` 落盘造成的。

**修法**：`core/source/SourceTest.ets` + `SourceEngine.ets`（纯追加）+ `views/SourceSettingsView.ets`
- 自检前快照当前音源 id + sandbox env，`finally` 里**无条件还原**（失败也把 last-active 改回去）；
- 自检解析出的 URL 与示例 musicInfo 对应缓存（`MediaCache` 地址条目 + `AudioCache` 文件）**按 key/quality 精确清理**（只删等于本次 URL 或示例 URL 的那条，不误伤同 key 正常地址）；
- 历史污染自愈：若自检前当前音源就是示例源，按「没有音源」清现场；
- **新增**：清理列表里历史残留的示例源条目（身份键 = 内置脚本名字+版本+作者，正在用的那个跳过）；
- 状态行改成可核对文案：`离线自检通过 · 当前音源仍是「星海音乐源」`。

### 4.2 多选退出后顶栏残留「已选中 N 项」、取消键点不动（中）

**真机现象**：歌单/在线列表长按进多选，退出后顶栏一直停在「已选中 1 项」，左上 ✕ 无效，只能用系统返回键。

**根因**（有真机 layout dump 佐证）：
1. `SelectSession.end()` 里有 `if (!this.isActive()) return;` —— **收尾被做成了有条件**，重复 end（exitSelecting 一次 + aboutToDisappear 一次是常态）后续全被挡掉，计数永远停在最后一次发布值；
2. `end()` 把 `onCancel` 换成空函数，而顶栏那颗 ✕ 调的就是它 ⇒ 残影上的取消成了**死键**；
3. 页面实例被重建时没人归零全局会话。

**修法**：
- `ui/Selection.ets`：`end()` 去掉早退，**无条件幂等**归零 actions/回调/三个 AppStorage 键；
- `pages/Index.ets`：标题栏判断改为 `!selectBarActive || !SelectSession.isActive()`（现读兜住一拍延迟）；残影态左上 ✕ 改为 `pathStack.pop()` 当返回，不再卡死；
- 六个列表页（歌单详情 / 在线列表 / 最近播放 / 本地音乐 / 下载管理 / 云端音乐）`aboutToAppear` 统一先归零再读数据。

### 4.3 我的页出现两条同名歌单（低，但定性纠正）

**原判断有误**（先被写成「导入+收藏各一条」）。真机拉库核对：`list.json` 里两条记录 **id 完全相同**（`wy_3e60770e…`），`sourceListId` 是整条分享链接的旧口径；即**同步数据里同一条记录被写了两份**，客户端照单全收。

**修法**：
- 写入幂等：`importPlaylist` 的 id 按**归一化 key** 算，id 未命中再按归一化 `sourceListId` 认领老记录（老口径 `wy__<链接>` 与新口径 `wy__id` 视为同一张），原地更新并把 sourceListId 迁到规范形态；
- 新增 `normalizeSourceListId()`（复用 `PlaylistLink` 解析器，不另写平台正则）；`createPlaylist` 的 id 加 seq 后缀防同毫秒撞 id；
- 展示层**只读去重**（`playlistSummaries` 按 id 去重，不改数据、不动同步 md5，避免下次连接多弹一次「选择同步方式」）；
- 同名不同来源的用副标题区分：`平台 · N 首` / `N 首`；`ForEach` key 加下标防撞。

### 4.4 冷启动首页「推荐」标题与内容重叠（低，偶发）

**根因**：壳层把窗口避让测量排在 `setTimeout(…, 500)`，`topInset` 首帧为 0；而 `List.contentStartOffset(topInset + 6)` **只在首次布局取一次值**，等 topInset 到齐也不重排 ⇒ 内容永久顶在标题栏下（约 38vp 偏移），偶尔在 500ms 内量完的启动才正常。

**修法**：`views/RecommendView.ets` 改用**真实占位 ListItem**（高度 `topInset + 6 − ROW_GAP`，高度变化必然重排），删掉 `contentStartOffset`；`views/PlaylistSquareView.ets` 有同类隐患，一并按同样方式修。

### 4.5 埋点缺口（自测中发现，自修）

复播走本地缓存时不出耗时日志 ⇒ 在 `PlaySession` 的「已下载文件 / 沙箱缓存」两条分支补 `StartupTiming.beginBuffer(..., true)`，现在复播能打出 `resolve=0ms buffer=39ms 命中缓存=true`。

## 七、遗留问题与建议（按优先级）

1. **【高】星海音源 403 授权**：真机后端原文 `{"code":403,"msg":"该音源仅对认证用户开放：请使用卡密、星海 App 或网页端访问"}` —— 这才是「QQ 音乐源不可用」的真实原因（不是 Q 封端口）。目前全靠自动换源兜底。**建议**：音源设置页把这类 403 识别成「需要认证」并给出引导，而不是每次起播弹一次换源提示。
2. **【中】探索页不刷新**：`ExploreView` 只在 `aboutToAppear` 调 `refresh()`，tab 页实例常驻 ⇒ 会话内不会重新拉池子（池子约 175 首，够刷一晚）。**建议**：加「池子年龄 > N 小时则重进刷新」的节流。
3. **【中】换源只覆盖「取地址失败」**：若源能解析出 URL 但播放时 403/404，仍走原有坏缓存重试，不触发换源。**建议**：把同一个 `switchSourceAndResolve` 入口接到播放失败分支（单入口已留好，成本低）。
4. **【中】PlaySession 只对「来自缓存的地址」重试一次**：新解析出的坏地址（源给出 4xx URL）会直接报错。属既有设计，可选加固。
5. **【低】HeartCache 不存 `freshBoost`**：冷启动缓存路径用位次近似。要把缓存也做准需给缓存加字段并升 `CACHE_VERSION`。
6. **【低】HDS 标题栏复用风险**：若某页仍偶发残影，只剩「HDS 对已压栈目的地只吃第一次下发的 options」这一种可能；当前兜底已保证 ✕ 当返回、不会卡死。
7. **【低】多选四页已补归零**，其余未使用多选的页面无需处理。
