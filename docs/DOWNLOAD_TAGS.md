# 下载时嵌入封面与歌词

下载一首在线歌曲时，把封面与歌词**写进音频文件本身**，而不是只放在应用的数据里 ——
文件拷到别处（U 盘、别的播放器、系统音乐）封面和词跟着走。

本文记调研结论、取舍，以及实现出来的样子。

> 已实现（`core/download/TagWriter.ets` + `core/download/DownloadTags.ets`，
> 接入点在 `DownloadManager.runTask`）：mp3 写 ID3v2.3（APIC 封面 + USLT 歌词），
> flac 写 VORBIS_COMMENT + PICTURE；边下边写，不额外重写一遍文件；
> 下载列表里「已下载」后面显示嵌入结果。
> 没做：m4a / aac / ogg 等容器、逐字歌词（SYLT）、把内嵌歌词读回来显示，详见文末。

## 1. 先给结论：写标签要自己拼字节

系统里**没有**「往音频文件写标签」的 API，只有读的：

| API | 能力 | 用不用得上 |
| --- | --- | --- |
| `media.AVMetadataExtractor`（`@ohos.multimedia.media`） | **读**元数据（`fetchMetadata`）与内嵌封面（`fetchAlbumCover`） | 只读。本地音乐导入读封面用的就是它 |
| `media.AVRecorder.setMetadata` | 只作用于**正在录制**的文件，key 还要求 `com.openharmony.` 前缀 | 用不上 |
| `media.AVEditor` / `AVMuxer` | 重新封装音视频轨，等于把整首歌重编一遍 | 用不上（要解码重编码） |

所以 `TagWriter.ets` 按容器格式自己拼字节。两种容器的标签**位置不同**，
这是实现上最要紧的一点：

| 容器 | 标签位置 | 写法 | 状态 |
| --- | --- | --- | --- |
| mp3 | 文件**最开头**（ID3v2.3） | 开头写标签，音频原样跟在后面 | 已实现 |
| flac | `fLaC` 魔数之后、音频帧之前（元数据块） | 保留 STREAMINFO，接上自己的 VORBIS_COMMENT / PICTURE | 已实现 |
| m4a / aac / ogg / wav | m4a 要改 `moov.udta.meta.ilst`（原子结构，可能牵动整个文件偏移） | 暂不做 | 未实现，列表里如实说明 |

mp3 用 **v2.3 而不是 v2.4**：中文歌词必须靠 UTF-16（v2.3 的编码字节只有 latin1 与
带 BOM 的 UTF-16 两种，UTF-8 是 v2.4 才有的），v2.3 的兼容面也更宽。
帧长在 v2.3 里是普通大端整数，v2.4 是「同步安全整数」，两者不通用。

## 2. 为什么是「边下边写」而不是「下完再改」

最省事的写法是下完再重写一遍文件（读出全文 -> 前面插标签 -> 再写回去），
但每首歌都要多一次全量读写：一首 30 MB 的 flac 就是多写 30 MB。所以改成边下边写：

1. 开头一小段先**攒在内存里**（最多 `MAX_HEAD` = 512 KB），从魔数认容器；
2. 认出 mp3：把 ID3v2.3 标签写出去，再补上攒下的部分（源文件自带的 ID3v2 标签整段跳过，
   免得两个标签叠在一起），之后的音频数据直写文件；
3. 认出 flac：顺块头走完源文件自己的元数据区，把 `STREAMINFO` 原样搬过来，
   接上我们要写的文字 / 封面块（最后一块的「last」标志由我们自己设），
   再把攒下的音频帧补上，之后直写；
4. 认不出 / 攒超上限：**把攒下的原样写出去**，音频一点不受影响，只是这一首没有标签。

代价是每次下载多认一次开头（通常几 KB，实际只多一次 64 KB 级别的内存搬运）。
文件写出的顺序与位置由 `TagSink` 保证，调用方（`DownloadManager`）只管喂数据。

## 3. 封面与歌词从哪来

`DownloadTags.collectDownloadTags` 与**播放页取封面 / 歌词同一批来源、同一顺序**
（不另起一套接口）：

- 封面：条目自带的 `coverUrl` -> `musicInfo.img` -> 封面地址缓存（`MediaCache.getPic`）
  -> 平台接口现查（`fetchMusicPic`，kw / kg 的搜索结果不带封面，只能现查）。
  拿到地址后下原图，从图片头里读出真实格式与尺寸（PNG 的 IHDR / JPEG 的 SOF 段）——
  尺寸是 flac PICTURE 块的必填字段，而 MIME 以实际字节为准，不信任地址后缀。
- 歌词：歌词缓存（`MediaCache.getLyric`）-> 源脚本的 `lyric` action
  -> 内置平台歌词（`fetchPlatformLyric`，kw / kg / tx / mg / wy）。
  有译文且两边都带时间轴时合成**双语 LRC**（译文那行紧跟原文、同时间标签），
  这是双语 LRC 的通行写法。

## 4. 容错：标签不能把下载弄坏

- 封面与歌词的网络请求与「解析播放链接」**同时开跑**，总超时 12 秒（`COLLECT_TIMEOUT_MS`）；
  超时或失败就当作没有那一项，**不抛给下载流程** —— 音源失效时下载照样成功。
- 封面原图上限 6 MB，超过或认不出格式（webp / gif / 下回来一页 HTML）就不嵌封面。
- 封面下载单独带 `User-Agent`：部分图床对空 UA 直接拒绝。
- 下载被取消 / HTTP 失败时，半截文件照旧删掉，标签逻辑不改变原有收尾。

## 5. 怎么看有没有嵌进去

- **应用内**：我的 - 下载管理里，已完成那条的副标题会显示 `已下载 4.2 MB · 已嵌入封面与歌词`；
  m4a 等容器会显示 `m4a 暂不支持写入标签`。
- **文件本身**：把下载的文件用「本地音乐」导入回来 —— 导入走的 `AVMetadataExtractor`
  读内嵌封面，能显示封面就说明 APIC / PICTURE 块写得对（歌词要等「内嵌歌词回读」做了才看得到）。
- 也可以把文件拷到电脑上用别的播放器打开看封面与歌词。

## 6. 没做的

- **m4a / aac / ogg**：m4a 要改 `moov` 里的原子结构（`moov` 常在最前面，
  插标签会牵动整个文件的偏移），风险与工作量都比 mp3 / flac 大；aac / ogg 同理各有各的容器结构。
  当前下载里 m4a 只对应全景声音质，占比很低，先在列表里如实说明。
- **逐字歌词（SYLT）**：写的是 USLT（整段 LRC 文本，播放器按时间轴自己滚），
  逐字歌词要 SYLT + 每字的毫秒偏移，只有部分播放器认。
- **内嵌歌词回读**：本地音乐导入现在还只读内嵌封面（歌词读的是同目录 `.lrc`），
  自己下载的文件里的 USLT / LYRICS 暂时不会被读出来显示。
